HTTP/2 over TCP vs QUIC/HTTP/3
This is where your TCP knowledge becomes practical.

1. First: what problem was HTTP/2 trying to solve?
Before HTTP/2, with HTTP/1.1, browsers often had to make multiple requests like:




Plain Text
GET index.html
GET style.css
GET app.js
GET logo.png
GET image1.png
GET image2.png
In HTTP/1.1, requests were not multiplexed efficiently over one connection. So browsers often opened multiple TCP connections to the same server to fetch assets in parallel.

HTTP/2 improved this by introducing multiplexing.

2. What is multiplexing?
Multiplexing means:

Multiple logical request/response streams share the same underlying connection.

So instead of this:




Plain Text
TCP connection 1 → HTML
TCP connection 2 → CSS
TCP connection 3 → JS
TCP connection 4 → image
HTTP/2 can do this:




Plain Text
One TCP connection
├── Stream 1: HTML
├── Stream 2: CSS
├── Stream 3: JS
├── Stream 4: image
This is very powerful because HTTP/2 can send many requests at the same time over a single TCP connection.

3. Then what is the problem?
Here is the key issue:

HTTP/2 multiplexes at the application layer, but it still runs over TCP.
And TCP provides one ordered byte stream.

From what we learnt earlier:

TCP must deliver bytes to the application in order.

So even if HTTP/2 has multiple logical streams inside one TCP connection, TCP itself does not understand those independent HTTP/2 streams.

TCP only sees:




Plain Text
byte 1, byte 2, byte 3, byte 4, byte 5...
It does not think:




Plain Text
Stream 1
Stream 2
Stream 3
Stream 4
That distinction is everything.

4. HTTP/2 head-of-line blocking over TCP
Let’s say HTTP/2 sends data like this over one TCP connection:




Plain Text
TCP byte stream:
[Stream A data][Stream B data][Stream C data][Stream D data]
Now imagine one TCP packet containing part of Stream A is lost.

Even if packets for Stream B, C, and D arrive successfully, TCP cannot deliver later bytes to HTTP/2 until the missing earlier TCP bytes are recovered.

Why?

Because TCP promises ordered byte delivery.

So the application waits.

This is called:

TCP-level head-of-line blocking
The QUIC specification explicitly addresses this kind of issue by providing multiple streams over QUIC, and QUIC documentation states that loss or blocking on one stream does not stall other streams.

5. Important distinction: HTTP/2 solved one HOL problem but not another
This is a very interview-worthy point.

HTTP/1.1 problem
Requests were often blocked at the HTTP request level.

Example:




Plain Text
Request 1 must finish before Request 2 progresses efficiently
HTTP/2 improved this using multiplexing.

HTTP/2 remaining problem
HTTP/2 still sits on top of TCP.

So if TCP loses an earlier packet, the whole TCP byte stream may wait.

That means:




Plain Text
One lost TCP segment
↓
TCP waits to recover it
↓
HTTP/2 cannot receive later bytes
↓
Multiple HTTP/2 streams may be delayed
So:

HTTP/2 removes much of the application-layer request blocking, but it cannot remove TCP-level head-of-line blocking.

This is why QUIC became important.

6. Enter QUIC
QUIC is defined in RFC 9000 as a UDP-based, multiplexed, secure transport protocol. It provides flow-controlled streams, low-latency connection establishment, and network path migration.

In simple words:

QUIC takes many things TCP + TLS + HTTP/2 needed separately and redesigns them together over UDP.

QUIC uses UDP underneath, but QUIC itself adds many transport features:

connections,
encryption,
streams,
reliability,
flow control,
congestion control,
loss recovery,
connection migration.
So do not think:

“QUIC uses UDP, so it is unreliable.”

Better mental model:

“QUIC uses UDP as a base, then builds a modern reliable transport on top of it.”

7. Why build QUIC on UDP?
Good question.

TCP is usually implemented in the operating system kernel. Changing TCP behaviour globally is slow because it depends on OS updates, middleboxes, network devices, and years of compatibility.

UDP is simpler and widely allowed across the internet. By building QUIC over UDP, QUIC can evolve more easily in user space.

RFC 9000 explicitly says QUIC packets are carried in UDP datagrams to facilitate deployment in existing systems and networks.

So UDP is used as the outer carrier, while QUIC implements richer transport behaviour above it.

8. QUIC streams: the big improvement
QUIC provides multiple independent streams inside one QUIC connection.

Conceptually:




Plain Text
QUIC connection
├── Stream 1: HTML
├── Stream 2: CSS
├── Stream 3: JS
├── Stream 4: image
This sounds similar to HTTP/2 multiplexing, but the difference is deeper:

In HTTP/2 over TCP
Multiplexing is above TCP.




Plain Text
HTTP/2 streams
↓
single TCP ordered byte stream
↓
IP
If TCP loses one earlier packet, later bytes are blocked.

In HTTP/3 over QUIC
Multiplexing is part of QUIC transport itself.




Plain Text
HTTP/3 streams
↓
QUIC streams
↓
UDP
↓
IP
QUIC understands independent streams, so loss affecting one stream does not necessarily block other streams. RFC 9000 says application protocols exchange information over QUIC via streams, and QUIC provides feedback for reliable delivery and congestion control. It also states that application protocols use ordered byte streams, with bidirectional and unidirectional streams.

9. Example: HTTP/2 packet loss
Imagine a page loading:




Plain Text
Stream A: HTML
Stream B: CSS
Stream C: JavaScript
Stream D: image
With HTTP/2 over TCP:




Plain Text
TCP packet #1: HTML bytes
TCP packet #2: CSS bytes
TCP packet #3: JS bytes
TCP packet #4: image bytes
Now packet #2 gets lost.

Even if packet #3 and #4 arrive, TCP cannot deliver them upwards until #2 is recovered, because TCP preserves strict byte order.

So JS and image data may wait behind the missing CSS bytes.

That is TCP head-of-line blocking.

10. Example: HTTP/3 over QUIC packet loss
Now with HTTP/3 over QUIC:




Plain Text
QUIC Stream A: HTML
QUIC Stream B: CSS
QUIC Stream C: JavaScript
QUIC Stream D: image
Suppose one packet containing CSS stream data is lost.

QUIC can continue delivering data for other streams if their data is available and not dependent on the missing stream data.

So:




Plain Text
CSS stream waits for recovery
JS stream can continue
image stream can continue
HTML stream can continue
That is the major practical win.

RFC 9000 describes QUIC as supporting streams and states that stream data is ordered within streams, while its overview explains QUIC’s stream-based structured communication and loss/congestion feedback.

11. Does QUIC completely eliminate head-of-line blocking?
Careful answer:

QUIC removes TCP connection-level head-of-line blocking between independent streams.
But within a single QUIC stream, data is still ordered.

So if Stream B loses data:




Plain Text
Stream B chunk 1
Stream B chunk 2 ← lost
Stream B chunk 3
Stream B itself may wait for chunk 2 before delivering chunk 3 in order.

But other streams do not have to wait.

So:




Plain Text
HTTP/2 over TCP:
Loss can block all streams sharing that TCP byte stream.
 
HTTP/3 over QUIC:
Loss usually blocks only the affected QUIC stream.
That is the precise understanding.

12. QUIC also improves connection setup
Classic HTTPS over TCP often involves:




Plain Text
TCP handshake
↓
TLS handshake
↓
HTTP request
QUIC combines cryptographic and transport handshakes. RFC 9000 explicitly says QUIC’s handshake combines negotiation of cryptographic and transport parameters and integrates TLS. It also says the handshake is structured to permit application data as soon as possible, including 0-RTT in some cases when prior communication/configuration allows it.

So QUIC can reduce connection setup delay compared with the traditional TCP + TLS layering.

13. QUIC connection migration
This one is very practical.

TCP connections are identified by a 4-tuple:




Plain Text
source IP
source port
destination IP
destination port
If your network changes — for example Wi-Fi to mobile data — the IP/port path may change, and TCP connections can break.

QUIC uses connection IDs. RFC 9000 says QUIC connections are not strictly bound to a single network path, and connection migration uses connection identifiers to allow connections to transfer to a new network path.

So QUIC is better suited for mobile and changing-network conditions.

15. Why not replace TCP everywhere with QUIC?
Because TCP is still extremely useful and mature.

Use TCP when:

the ecosystem already expects TCP,
the protocol is built for TCP,
you need broad compatibility,
you do not need QUIC’s stream/migration/setup advantages.
Use QUIC when:

you want modern encrypted transport,
you need HTTP/3,
you care about connection setup latency,
you want multiple independent streams,
you want better behaviour during network changes.
Important: QUIC is not “always faster” in every situation. It gives better design properties for many web/mobile scenarios, but real performance depends on network conditions, implementation, server support, and workload.

Phase 2 — QUIC: modern transport over UDP
QUIC is defined in RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport as the core QUIC transport protocol; it provides flow-controlled streams, low-latency connection establishment, network path migration, and security measures for confidentiality, integrity, and availability.

The important mental model is:




Plain Text
UDP is the simple carrier.
QUIC is the smart transport built on top.
HTTP/3 runs over QUIC.
RFC 9114: HTTP/3 says HTTP/3 is a mapping of HTTP semantics over QUIC, and highlights QUIC features useful for HTTP: stream multiplexing, per-stream flow control, and low-latency connection establishment.

1. Why was QUIC invented?
You already learnt TCP deeply, so let’s start from TCP’s pain points.

Problem 1 — TCP has connection setup cost
Traditional HTTPS commonly involves:




Plain Text
TCP handshake
↓
TLS handshake
↓
HTTP request
RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says QUIC combines negotiation of cryptographic and transport parameters, integrates the TLS handshake, and is structured to permit application data as soon as possible, including 0-RTT when prior communication/configuration allows it.

So QUIC’s idea is:

Instead of TCP first, TLS later, transport parameters separately — combine these responsibilities into one modern handshake.

Problem 2 — TCP has connection-level head-of-line blocking
TCP delivers one ordered byte stream. If an earlier TCP segment is lost, later bytes are blocked from delivery until the lost segment is recovered. We already covered this with HTTP/2 over TCP.

QUIC solves this at the transport level by using independent streams. RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says application protocols exchange information over a QUIC connection via streams, and streams are ordered sequences of bytes; it also distinguishes bidirectional and unidirectional streams.

Your internal learning file d60fa09a-c4b5-4e31-9dbd-5d049c6c8f49 also states that QUIC is based on UDP, introduces streams as first-class citizens at the transport layer, and that packet loss affecting one stream usually does not affect others.

Problem 3 — TCP connections are tied to network path
A TCP connection is practically tied to the source/destination IP and port combination. If your device moves from Wi-Fi to mobile data, the TCP path can break.

RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says QUIC supports network path migration and uses connection identifiers to allow connections to transfer to a new network path.

So QUIC is especially interesting for mobile or unstable networks.

2. What exactly is QUIC?
QUIC is not just UDP.

UDP by itself gives minimal datagram delivery and does not guarantee delivery, ordering, or duplicate protection, as defined in RFC 768: User Datagram Protocol.

QUIC uses UDP underneath, but QUIC itself adds richer transport behaviour: secure connection setup, streams, flow control, loss detection, and congestion-control support. RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport explicitly describes QUIC as a secure, connection-oriented protocol that exchanges QUIC packets carrying frames with control information and application data.

So the clean definition is:

QUIC is a secure, connection-oriented, multiplexed transport protocol built on top of UDP.

This is different from HTTP/2:




Plain Text

The key change is that HTTP/3 does not use TCP; it uses QUIC over UDP.

8. Does QUIC provide reliability?
Yes — but not in the same way as TCP’s single ordered byte stream.

RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says QUIC provides feedback needed to implement reliable delivery and congestion control.

The better mental model is:




Plain Text

Reliable delivery over independent streams within a QUIC connection
QUIC streams are ordered internally, but because the transport understands multiple streams, one stream’s missing data does not necessarily block other streams.

9. Does QUIC have ACKs?
Yes, but be careful with the mental model.

TCP ACKs acknowledge byte positions in one ordered byte stream. QUIC uses transport-level feedback for reliable delivery and congestion control, and RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport states that QUIC provides the necessary feedback to implement reliable delivery and congestion control.

For now, remember:




Plain Text

10. QUIC flow control
QUIC has flow control, but unlike TCP it supports stream-level thinking.

RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says QUIC provides applications with flow-controlled streams.

RFC 9114: HTTP/3 also calls out per-stream flow control as a desirable QUIC feature for HTTP.

Mental model
In TCP:




Plain Text

In QUIC:




Plain Text

The source snippets explicitly support QUIC’s flow-controlled streams and HTTP/3’s per-stream flow control; the “individual + overall connection” phrasing is the standard conceptual model, and I’m using it here as a teaching simplification based on QUIC’s stream design.

11. QUIC congestion control
QUIC still needs congestion control because it runs over the same Internet and must not flood the network.

RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says accompanying documents describe loss detection and an exemplary congestion-control algorithm, and it also says QUIC provides feedback necessary to implement reliable delivery and congestion control.

Important point:

QUIC uses UDP as a carrier, but it does not mean QUIC ignores congestion.

That matters because raw UDP does not provide congestion control, while QUIC builds transport behaviour above UDP.

12. QUIC connection migration
This is one of the features that makes QUIC feel modern.

RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says QUIC connections are not strictly bound to a single network path, and connection migration uses connection identifiers to allow connections to transfer to a new network path.

Example

↓

↓

Conceptually:




Plain Text
Stream 1 → HTML
Stream 2 → CSS
Stream 3 → JS
Stream 4 → image
Step 4 — Packet loss happens
Suppose one packet contains data for CSS stream and gets lost.

In HTTP/2 over TCP, that loss can block later bytes in the TCP stream. In QUIC, your internal file d60fa09a-c4b5-4e31-9dbd-5d049c6c8f49 states that QUIC streams are delivered independently and packet loss affecting one stream usually does not affect others.

So conceptually:




Plain Text
CSS stream waits for missing data
JS stream can continue
Image stream can continue
HTML stream can continue
This is the key performance idea.

17. Does QUIC eliminate all head-of-line blocking?
No — careful and precise answer:

QUIC reduces connection-level head-of-line blocking between independent streams, but each stream is still an ordered sequence of bytes. RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says streams are ordered sequences of bytes.

So:




Plain Text
Loss inside Stream A can block later data inside Stream A.
But it does not necessarily block Stream B, Stream C, Stream D.
That is the precise understanding.

18. QUIC limitations and trade-offs
Let’s be honest — QUIC is powerful, but not magic.

Limitation 1 — It depends on UDP reachability
QUIC runs over UDP, so networks that block or degrade UDP can affect QUIC. The source-backed part is that QUIC is UDP-based, as stated in RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport.

The operational concern about UDP reachability is a practical implication, not directly stated in the RFC snippet above.

Limitation 2 — More logic moves above the OS TCP stack
QUIC implements transport functionality over UDP. RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport defines QUIC packet exchange, stream handling, security, flow control, loss detection support, and congestion-control support.

The practical implication is that QUIC implementations carry more protocol responsibility than a simple UDP application.

Limitation 3 — 0-RTT has conditions
0-RTT is not always available. RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport says clients can send data immediately using 0-RTT only with some form of prior communication or configuration.

So do not say:

“QUIC always sends data immediately.”

Say:

“QUIC can support 0-RTT for repeat connections when conditions allow.”

19. Interview-ready answer
If someone asks:

“What is QUIC and why does HTTP/3 use it?”
You can say:

QUIC is a secure, connection-oriented, multiplexed transport protocol built over UDP. It provides flow-controlled streams, integrates TLS into the transport handshake, supports low-latency connection establishment, and enables network path migration. HTTP/3 maps HTTP semantics over QUIC, using QUIC’s stream multiplexing and per-stream flow control to avoid the TCP-level head-of-line blocking that remains in HTTP/2 over TCP.

That is a strong system-design-level answer.

11) Edge cases and failure modes — what interviewers want you to mention
Communication-heavy systems fail in very predictable ways.

A. Packet loss
With TCP, lost packets are retransmitted automatically. TCP’s reliability comes from acknowledgement, retransmission, ordering, and connection management.
With UDP, lost packets are not automatically recovered in the same way. UDP is connectionless and does not guarantee delivery or order.
Design lesson
If late data is useless, prefer the low-latency path.
The transport-layer trade-off is explicitly highlighted by the web sources and by Designing Data-Intensive Applications, which says UDP is suitable where delayed data is worthless, such as in VoIP.

B. Slow downstream service
Example:




Plain Text
Client → API Gateway → User Service (fast)
                      → Feed Service (slow)
The whole request may feel slow even if only one dependency is slow.

How to handle
This is my design guidance:

add timeouts
use partial responses where acceptable
fail gracefully
avoid unbounded fan-out on the critical path
C. Retry storms
If 100,000 clients all retry immediately after a timeout, you can overload the service more severely than the original issue.

Good practice
My design guidance:

exponential backoff
jitter
retry only safe/idempotent operations when possible
That ties directly to HTTP semantics:

GET, PUT, and DELETE are idempotent in the HTTP sense, meaning the same request repeated results in the same final server state.
D. Chattiness explosion
A single UI screen may trigger too many backend calls.
The internal cloud application design file explicitly warns that microservice architectures increase chattiness because smaller services naturally increase cross-service calls.

Fixes
My design guidance:

API gateway aggregation
batching
caching
denormalised view models for read-heavy screens
E. Head-of-line user experience problems
If a user-facing response waits on one slow component, the whole experience slows down.

Example
feed API waits for ads service
ads service is slow
feed looks broken
Response
My design guidance:

isolate optional dependencies
degrade gracefully
return core content first

Deep design lesson
At very large scale:

communication between web servers and caches becomes its own design problem

“fast path” infrastructure can grow into a critical dependency

2) DNS — the internet’s phonebook
What problem DNS solves
Humans prefer names like:




Plain Text
example.com
But machines need an IP address. DNS translates the human-readable domain name into a machine-usable IP address. The sources explicitly describe DNS as the system that maps domain names to IP addresses so browsers know where to connect.

DNS lookup — slow explanation
Step 1: Browser cache
The browser may already have a cached answer for the domain. If the answer is still valid, it can stop there. The browser-cache-first behaviour is explicitly described in the DNS browser lookup source.

Step 2: OS cache
If the browser does not know, the operating system may have a cached DNS record. That same source describes the OS cache as the next place checked.

Step 3: Resolver
If no local cache has the answer, the DNS resolver is queried. Multiple sources describe the resolver/recursive resolver as the component that continues the lookup on behalf of the client.

Step 4: Root → TLD → Authoritative
The resolver may contact:

Root name servers
Top-level domain (TLD) servers, like .com
Authoritative name servers, which provide the final answer for the domain
This multi-step hierarchy is explicitly described in the DNS lookup sources.

Easy analogy
Think of DNS like asking for someone’s house address:

Browser cache = “I already remember it”
OS cache = “my device remembers it”
Resolver = “let me ask the directory service”
Root/TLD/Authoritative = “ask the right office, then the right district, then the actual owner of the address”
That analogy is my explanation, but the hierarchy itself is directly supported by the DNS sources.

Interview answer: “What happens in DNS lookup?”
A strong answer is:

The client first checks local caches. On a miss, it sends the query to a resolver, which walks the DNS hierarchy: root server, TLD server, then authoritative name server, and returns the IP address. The result is usually cached for future lookups.

3) IP address vs port — do not confuse them
This is one of the most important beginner topics.

IP address
An IP address identifies the machine/device on the network. Multiple sources explain that the IP address identifies the host/device.

Port
A port identifies the application or service on that machine. Multiple sources explicitly say that a machine can run multiple applications, and port numbers let the transport layer distinguish which application should receive the data.

Example
If a server machine is:




Plain Text
203.0.113.10
Then:

web traffic may go to port 80 for HTTP
secure web traffic may go to port 443 for HTTPS
DNS commonly uses port 53
Beginner analogy
IP address = the building address
Port = the flat/apartment number
This exact style of analogy is explicitly used in the ports/sockets material.

4) Port ranges — useful interview detail
One ports guide says a port number uses 16 bits and ranges from 0 to 65535. It also breaks them into:

0–1023 well-known ports
1024–49151 registered ports
49152–65535 client/dynamic/ephemeral ports
Another source says ephemeral/dynamic client ports are typically generated for short-term use and can come from 1024 to 65535.

Practical meaning
When your browser talks to a web server:

the server usually listens on a well-known port like 80 or 443
the browser/client usually uses a temporary high-numbered port assigned dynamically
5) Socket — the real communication endpoint
This is the next piece of the puzzle.

What is a socket?
A socket is a communication endpoint involving an IP address and a port number. Multiple sources define a socket using the combination of IP address and port, or as one endpoint of a communication link identified that way.

Example
If:

your laptop uses 192.168.1.5:54321
the server uses 203.0.113.10:443
then each side has its own socket.
The client and server communicate between those endpoints. The sources explicitly describe these client and server socket endpoints and examples of browser connections using a high client port and a standard server port.

Why sockets matter in system design
This is what lets:

one machine run many services
one browser open many connections
one app talk to many backends
That implication is my design explanation, but it follows directly from the sources that ports distinguish applications and sockets identify communication endpoints.

6) TCP sockets vs UDP sockets
A sockets source explains two broad types:

stream sockets → connection-oriented, associated with TCP
datagram sockets → connectionless, associated with UDP
Meaning
TCP socket = reliable, ordered byte stream
UDP socket = lightweight message sending without the same delivery guarantees
This distinction is explicitly described in the socket and TCP/UDP sources.

7) TCP connection setup — the actual “hello”
Before HTTP over TCP can send useful application data, TCP establishes a connection.

The 3-way handshake
The TCP sources explain that TCP uses:

SYN
SYN-ACK
ACK
Slow explanation
Step 1 — SYN
The client says:

“I want to start a connection.”

Step 2 — SYN-ACK
The server replies:

“I heard you, and I’m ready.”

Step 3 — ACK
The client says:

“Great, let’s begin.”

That exact packet naming and order are directly supported by the sources.

Why this matters
Because TCP is not “fire and forget”. It is connection-oriented and wants both sides to agree before data starts flowing. The TCP sources explicitly say TCP is connection-oriented and establishes a connection before transmission.

Interview answer: “Why is TCP slower than UDP?”
A strong answer is:

TCP has setup overhead from the handshake and then maintains reliability through acknowledgements, retransmissions, ordering, flow control, and congestion control. UDP skips most of that, so it is lighter and faster, but less reliable.

10) Keep-alive — why reusing connections matters
One source on HTTP evolution says HTTP/1.1 introduced persistent connections, allowing multiple requests over a single TCP connection and reducing the overhead of repeatedly opening and closing connections. Another source says HTTP/1.1 has persistent connections / keep-alive as a key feature.

Why keep-alive matters
Without connection reuse:

every request would need a new TCP handshake
HTTPS would also pay repeated security setup cost
latency and server overhead would increase
The repeated connection overhead reduction is explicitly why persistent connections were introduced according to the HTTP/1.1 sources.

Interview angle
If an interviewer asks:

“Why does connection reuse matter?”

A strong answer is:

Reusing connections reduces the cost of repeatedly opening TCP connections and, for HTTPS, avoids repeatedly paying full setup overhead. That lowers latency and improves resource efficiency on both clients and servers.

11) HTTP/1.1 vs HTTP/2 vs HTTP/3 — the beginner-to-interview view
You asked not to rush, so for now let’s keep this high-level.

HTTP/1.1
Key points from sources:

text-based protocol
persistent connections / keep-alive
struggles with modern workloads because one slow request can hurt performance, and clients often open multiple connections to work around the limitation
HTTP/2
Key points from sources:

multiplexing: multiple streams over one connection
header compression (HPACK)
binary framing instead of plain text style framing
still tied to TCP, so packet loss at the TCP level can still affect all streams on that connection
HTTP/3
Key points from sources:

built on QUIC
QUIC runs over UDP
designed to reduce latency and improve handling of loss compared with TCP-based HTTP/2
QUIC integrates encryption and transport setup more tightly, reducing handshake overhead according to the QUIC sources
Simple interpretation
HTTP/1.1 = older, simpler, more connection overhead
HTTP/2 = more efficient use of one connection
HTTP/3 = aims to reduce latency further by moving to QUIC over UDP
That summary is directly supported by the version-comparison and QUIC sources above.

How to pick the right pattern in interviews
1) Start with the core problem
Traditional HTTP was built around a simple model:




Plain Text

That works well when the client is happy to ask every time it needs information. But it breaks down when the server needs to push updates to the client as soon as something changes. One real-time communication guide explicitly says the classic web model is request/response and that the challenge is how to break out of those synchronous constraints when you need server-driven updates.

Examples of systems that need “push”
chat messages
live dashboards
stock prices
live sports scores
multiplayer games
collaborative editing
The polling/WebSocket/SSE comparison sources use these exact kinds of examples.

2) Polling — the simplest real-time illusion
What polling is
Polling means:

the client asks the server for updates at fixed intervals

Example:




Plain Text
Every 5 seconds:
“Any new messages?”
The polling guide explains that short polling is the simplest approach: the client runs a timer and makes regular HTTP requests, and the server replies immediately each time.

Mental model
Think of polling like this:

A child asks every few seconds:
“Are we there yet?”
“Are we there yet?”
“Are we there yet?”

That is polling.

How it works



Plain Text
Client → HTTP request
Server → immediate response
Connection closes
Wait
Repeat
That request/response cycle is exactly how the polling references describe it.

Advantages
The polling references explicitly say polling is:

simple to implement
works with standard HTTP infrastructure
easy to scale statelessly
friendly with load balancers and normal web setups
Disadvantages
The same references say polling causes:

wasted requests when there is no new data
delayed updates because freshness depends on the polling interval
higher bandwidth and server load
it is not truly real-time
Best use cases
Polling is most suitable when:

updates are infrequent
simplicity matters more than freshness
true real-time behaviour is not required
Interview summary
Polling is the easiest option, but it wastes work because the client keeps asking even when nothing has changed. It is usually best only for low-frequency or simple update scenarios.

3) Long polling — “wait until there’s something new”
What long polling is
Long polling improves on normal polling.

Instead of the server replying immediately, it holds the request open until:

new data is available, or
a timeout occurs
Then the client sends another request.

The long polling references explicitly describe this mechanism: the server keeps the request open until new data arrives or the timeout is reached, then the client restarts the cycle.

Mental model
Imagine the child now asks:

“Tell me only when we reach the destination.”

The parent stays quiet until there is something meaningful to say.

That is long polling.

How it works



Plain Text
Client → “Any updates?”
Server → waits
If update happens → responds
If timeout happens → responds empty / timeout
Client → immediately sends next request
This loop is explicitly described in the long polling sources.

Advantages
The references say long polling:

gives near-real-time updates
reduces wasted requests compared to regular polling
works over standard HTTP
is useful when more modern push technologies are unavailable
Disadvantages
The same sources say long polling:

still has repeated request overhead
keeps server connections open longer
can create scalability issues with many clients
needs timeout handling carefully
Best use cases
Use long polling when:

you want better freshness than polling
you still need to stay in normal HTTP/legacy environments
updates are irregular or moderate frequency
Interview summary
Long polling is a compromise: better freshness than normal polling, but still more overhead and open-connection cost than true persistent streaming approaches.

4) SSE — Server-Sent Events
What SSE is
SSE is a one-way streaming connection from server to client over standard HTTP.
The server pushes updates down a single long-lived HTTP response.

The SSE references explicitly say SSE is unidirectional and is designed for server → client streaming over a persistent HTTP connection.

Very important idea
With SSE:

server can send updates to client
client cannot use the same connection to send data back to the server
That one-way nature is explicitly stated in the comparison sources.

Mental model
SSE is like subscribing to a live radio channel:

the broadcaster keeps speaking
listeners keep receiving updates
listeners do not talk back on the same channel
Advantages
The sources explicitly state that SSE offers:

server-to-client streaming
built-in automatic reconnection
simplicity
compatibility with HTTP infrastructure
good fit for notifications, dashboards, feeds, and streaming text updates
Disadvantages
The sources also say SSE:

is one-way only
is text/UTF-8 oriented
is not the right choice for two-way interactive systems
Best use cases
The SSE sources repeatedly position it for:

live dashboards
notifications
stock tickers / live feeds
log streaming
AI/token/text streaming type scenarios
Internal enterprise note
An internal architecture page Spark contains explicit discussion around choosing between polling and SSE, and it also explicitly mentions concerns about long-lived SSE or WebSocket connections in that environment because of infrastructure overhead and TLS connection impact on sidecars. It also explicitly discusses retry queues and DLQ decisions. That is a useful real-world reminder that protocol choice is not just about elegance; infrastructure constraints matter too.

Interview summary
Use SSE when you only need server → client updates and want a simpler HTTP-based streaming model with built-in reconnect.

5) WebSockets — full two-way real-time communication
What WebSockets are
WebSockets provide a persistent, full-duplex, bidirectional communication channel over a single TCP connection.

Multiple sources explicitly describe WebSockets this way.

What “full-duplex” means
It means:

client can send at any time
server can send at any time
both sides can talk independently after the connection is established
That is exactly how the WebSocket sources contrast them with HTTP.

How a WebSocket starts
A WebSocket connection starts with an HTTP handshake and then upgrades to the WebSocket protocol. The sources explicitly mention the upgrade request and the 101 Switching Protocols response.

Mental model
If SSE is like radio, WebSocket is like a phone call:

both sides can speak whenever they want
no need to reconnect for each message
ideal for interactive conversations
Advantages
The sources explicitly say WebSockets provide:

low-latency communication
persistent connection
bidirectional messaging
lower overhead than repeated HTTP polling
suitability for chat, gaming, collaborative tools, trading/live systems
Disadvantages
The references also note that WebSockets:

require WebSocket-aware infrastructure
usually need reconnection logic handled explicitly
add stateful connection management complexity
Best use cases
WebSocket is best when you need:

chat
multiplayer gaming
collaborative editing
bidirectional low-latency interactive systems
Interview summary
Use WebSockets when you need true bidirectional, low-latency communication. It is more capable than SSE, but also more operationally complex.

11) Backpressure — one of the most important advanced concepts
Now we move from beginner to strong intermediate level.

What is backpressure?
An internal excerpt from Designing Data-Intensive Applications explicitly frames the question:

What happens if producers send messages faster than consumers can process them?

It says systems broadly choose to:

drop messages
buffer them in a queue
apply backpressure / flow control, meaning block the producer from sending more until the recipient catches up
That is a brilliant interview definition.

Simple explanation
Backpressure means:

“Slow down — the receiver cannot keep up.”

Mental model
Imagine a water pipe:

if water enters faster than it exits,
pressure builds,
eventually something overflows or breaks
Backpressure is the mechanism that tells the sender:

reduce the rate

Why it matters
The backpressure references explicitly say that without proper flow control:

queues can silently grow
latency rises
error rates and DLQ volume can grow
overload can cascade through the system
Internal enterprise note
The internal 16- Integration Developer Training Track describes a system that delays incoming web service requests in an internal queue when request-per-minute or concurrent request limits are hit. That is not labelled “backpressure” in the document, but it explicitly describes delaying requests once limits are reached.

Interview summary
Backpressure is the control mechanism that prevents fast producers from overwhelming slow consumers. Common reactions are buffering, throttling/blocking the producer, or dropping work, depending on system requirements.

12) Dead Letter Queue (DLQ) — where failed messages go
What a DLQ is
A DLQ is a special queue for messages that fail processing after retries or are malformed / expired. This is explicitly stated in the DLQ references and in the internal cloud design material.

Why it exists
The DLQ sources explicitly say DLQs help to:

prevent message loss
isolate problematic messages
avoid blocking the main queue
make debugging and later reprocessing easier
Mental model
A DLQ is like a quarantine desk in a factory:

normal packages move through the main line
damaged/problematic packages are pulled aside
specialists inspect them later
the whole assembly line does not stop
Internal enterprise examples
11- Cloud based Application Design and Development explicitly shows Azure Service Bus queue configuration where MaxDeliveryCount is set and a message is automatically dead-lettered after the configured number of deliveries.
Spark explicitly discusses retry queues, whether to have single or per-tier DLQs, and capping retry counts before surfacing manual retry in the UI.
Interview summary
A DLQ is a safety net for unprocessable messages. Instead of losing them or endlessly retrying them, the system isolates them for investigation and possible replay.

14) Failure modes and edge cases
A. Polling overload
Too many clients polling too frequently increases wasted work and cost.

B. Long polling resource pressure
Held connections and repeated loops can create server scalability pressure.

C. SSE is the wrong tool for two-way systems
If the client must frequently send data back, SSE is not enough because it is one-way.

D. WebSocket infrastructure complexity
Persistent stateful connections require more careful operational handling.

E. Queue backlog growth

F. Poison messages
Bad messages can fail repeatedly and should be routed to DLQ after retry policy is exhausted.

1) Start with the most important truth
Distributed systems fail normally
This is the single biggest mindset change.

2) Retries — the first reliability pattern
What a retry is
A retry means:

“Try the same operation again after failure.”

The internal Microsoft microservices eBook explicitly discusses retries with exponential backoff and says they are used because cloud resources can be intermittently unavailable for short periods. It gives examples like containers moving for load balancing or a database temporarily becoming unavailable.

Why retries exist
Sometimes failure is temporary, not permanent.

Examples:

network hiccup
service startup
transient database failover
short overload period
The internal retry material explicitly frames retries as a solution for transient faults.

But retries are dangerous
Retries can also make systems worse:

duplicate requests
retry storms
overloaded downstream systems
double side effects
That is why retries must be paired with idempotency, backoff, and limits.

Exponential backoff
The internal microservices source explicitly says exponential backoff means retrying with an exponentially increasing wait time up to a maximum retry count.

Simple example
Instead of:




Plain Text
retry after 1s, 1s, 1s, 1s
Do:




Plain Text
retry after 1s, 2s, 4s, 8s
The “increasing wait time up to a retry limit” part is directly supported by the source.

Interview summary
Retries are for transient failures, but they must be bounded and usually combined with exponential backoff so the system does not overload a struggling dependency.

3) Idempotency — one of the most important concepts in all system design
What idempotency means
An operation is idempotent if doing it multiple times leads to the same final state as doing it once.

The HTTP method references explicitly define idempotency this way: multiple identical requests should result in the same final server state, even if responses differ.

HTTP examples
The sources explicitly say:

GET is idempotent
PUT is idempotent
DELETE is idempotent, even if later responses change from success to not-found
POST is generally not idempotent
Why idempotency matters in distributed systems
Because retries happen.

If a client sends a request, the server processes it, but the response is lost, the client may retry. If the operation is not idempotent, you may:

create duplicate orders
send duplicate emails
charge a payment twice
This connection between retries and idempotency is explicitly described by the idempotency references. They explain that idempotent methods can be safely retried when communication failures happen before the client reads the response.

Mental model
Idempotency is like a light switch with “turn off”:

pressing “turn off” once or five times gives the same final result: off
Non-idempotent is like “add 100 rupees”:

doing it once vs five times changes the final state
That analogy is my teaching aid, but the state-based definition is directly supported by the sources.

Interview summary
Idempotency is essential wherever retries are possible. It ensures repeated delivery or repeated API requests do not create duplicate side effects.

4) Delivery guarantees — at-most-once, at-least-once, exactly-once
This is very interview-important.

A) At-most-once
Meaning:

message may be delivered once
or may be lost
but not retried repeatedly
Trade-off
fewer duplicates
more risk of loss
This exact phrase is not explicitly laid out in the searched sources as a formal section, so I’m marking this as my explanatory framing based on reliability terminology.

B) At-least-once
Meaning:

message will be retried until processed/acknowledged
duplicates are possible
A message queue architecture guide explicitly says that in at-least-once delivery, the broker redelivers unacknowledged messages, and therefore consumers must be idempotent because processing the same message twice should have the same effect.

This is one of the best practical definitions you can remember.

C) Exactly-once
The queue architecture guide explicitly says:

True exactly-once is hard. Kafka achieves it with idempotent producers and transactional writes. Most systems approximate it with at-least-once delivery plus deduplication on the consumer side.

That is a fantastic interview line because it is honest and precise.

Interview summary
In practice, many systems use at-least-once delivery and rely on idempotent consumers plus deduplication. True exactly-once semantics are difficult and usually require specialised support.

5) Deduplication — what to do when duplicates happen
Why duplicates happen
Duplicates can happen when:

broker retries unacknowledged messages
network fails before acknowledgement is received
producer retries publishing
consumer crashes after side effect but before ack
The at-least-once description from the queue guide directly implies this redelivery/duplication problem.

The core idea of deduplication
Deduplication means:

detect repeated processing attempts and make sure the side effect is applied only once

This is a general design explanation from me, but it is directly motivated by the redelivery + idempotent consumer guidance in the queue architecture guide.

Common strategy (design guidance)
A typical pattern is:

include a unique message ID / request ID
store processed IDs
ignore duplicates
That is my design recommendation; the sources here support the need for idempotent consumers, but do not explicitly describe this exact step-by-step technique.

Interview summary
Under at-least-once delivery, duplication is expected. A robust system handles this with idempotent consumers and often with deduplication based on stable message or request identifiers. The source explicitly supports the idempotent consumer requirement, while the identifier technique is my design guidance.

6) Ordering — when event sequence matters
Why ordering matters
Some systems cannot tolerate out-of-order processing.

Examples:

bank account balance updates
inventory reservations
chat message sequence
user timeline events
What the source says
The message-queue architecture guide explicitly says:

ordering is guaranteed per partition in Kafka
ordering is guaranteed per queue in SQS FIFO
if you need related messages ordered, route them to the same partition using a consistent key
That is interview-grade material.

Important truth
Global ordering across a huge distributed system is expensive and difficult.

The source does not explicitly say the phrase “global ordering is expensive”, so I am marking that as my system design guidance.
But the source does explicitly say ordering is commonly per partition or per queue, not universal.

Mental model
Ordering is easiest when related events stay on the same conveyor belt.

If you spread them across many belts, preserving exact sequence becomes much harder.

Interview summary
Ordering is usually guaranteed only within a queue or partition, not across the whole system. If ordering matters for a given entity, send related messages to the same partition using a stable key.

7) Partitioning — how streams scale
What partitioning is
Partitioning means splitting a stream/topic into multiple independent lanes so multiple consumers can process in parallel.

The event-stream and message architecture guides explicitly mention partitions and say event streams support scalable parallel processing through partitioning.

Why partitioning exists
Without partitioning:

one consumer path becomes bottleneck
throughput is limited
scaling is hard
With partitioning:

work can be spread across multiple consumers
throughput grows
some ordering can still be preserved within a partition
The per-partition ordering property is explicitly supported by the source.

Trade-off
Partitioning improves throughput but weakens any idea of total global order.

That trade-off is my explanation built from the explicit “order guaranteed per partition” statement.

Interview summary
Partitioning is the main scaling strategy for streams. It enables parallelism, but ordering is then typically guaranteed only within each partition.

8) Fan-out — one event triggers many reactions
What fan-out means
Fan-out means one event causes multiple downstream consumers or workflows to react.

The message queue architecture guide explicitly contrasts:

point-to-point queue: one message delivered to one consumer path
pub/sub topic: one event can be broadcast to multiple subscribers/consumer groups
The stream references also explicitly say streams allow multiple consumers to process the same event independently.

Example
A single OrderPlaced event might fan out to:

payment
inventory
email
analytics
fraud detection
The stream and queue sources explicitly use e-commerce style examples where multiple independent services process event data.

Interview summary
Fan-out is a natural fit for pub/sub or event-stream systems where multiple consumers independently react to the same event.

9) Consumer groups — parallelism without everyone doing the same work
What a consumer group is
A consumer group lets multiple consumer instances share the work of reading a topic/stream together, instead of every instance processing every event.

The sources talk about distributing work across multiple consumers and about each consumer group getting its own copy in pub/sub-style architectures.

To stay disciplined: the sources do not provide a long formal definition of “consumer group” mechanics in the exact Kafka sense, so I’ll keep the explanation high-level.

Simple mental model
Think of:

topic = newspaper publisher
consumer group = one newspaper delivery company with many delivery people sharing routes
another consumer group = a completely different company with a different purpose
That analogy is my teaching aid, but it matches the “multiple consumers / subscribers / groups” behaviour described in the sources.

Interview summary
Consumer grouping is how streaming systems combine scaling and independence: workers inside the same group can share load, while different groups can independently consume the same event stream. This is a high-level design explanation based on the source descriptions of multiple consumers and group copies.

10) Circuit breakers — stop hammering a failing dependency
What a circuit breaker is
A circuit breaker is a resilience pattern that temporarily stops calls to a dependency that is repeatedly failing, so you don’t keep wasting requests and amplifying the outage.

The internal .NET microservices eBook’s additional resilience resources explicitly reference resiliency patterns and bulkhead, but the snippet shown does not explicitly define circuit breakers in detail.

So here I need to be careful:

Supported by source: resiliency patterns are relevant; fault handling and exponential backoff are discussed.
My design explanation: the specific “circuit breaker opens after repeated failures and prevents further calls temporarily” behaviour
Why it matters
Without a circuit breaker:

every caller keeps retrying
the failed service gets overwhelmed
recovery becomes harder
This is my reliability guidance, but it fits naturally with the source’s emphasis on transient fault handling and retries.

Interview summary
Circuit breakers are used to stop repeated calls to an unhealthy dependency and allow the system to fail fast or degrade gracefully instead of repeatedly overloading the failing service. This is my design explanation; the cited source supports the broader resiliency context.

This is my design interpretation, while the internal source explicitly supports the existence of request-per-minute and concurrency limits plus delay behaviour.

Interview summary
Rate limiting protects a system by capping request volume or concurrency. The internal source explicitly shows both concurrent-request limits and per-minute request limits, with excess requests delayed in an internal queue.

Asynchronism

Source: Intro to architecting systems for scale

Asynchronous workflows help reduce request times for expensive operations that would otherwise be performed in-line. They can also help by doing time-consuming work in advance, such as periodic aggregation of data.

Message queues
Message queues receive, hold, and deliver messages. If an operation is too slow to perform inline, you can use a message queue with the following workflow:

An application publishes a job to the queue, then notifies the user of job status
A worker picks up the job from the queue, processes it, then signals the job is complete
The user is not blocked and the job is processed in the background. During this time, the client might optionally do a small amount of processing to make it seem like the task has completed. For example, if posting a tweet, the tweet could be instantly posted to your timeline, but it could take some time before your tweet is actually delivered to all of your followers.

Redis is useful as a simple message broker but messages can be lost.

RabbitMQ is popular but requires you to adapt to the ‘AMQP’ protocol and manage your own nodes.

Amazon SQS is hosted but can have high latency and has the possibility of messages being delivered twice.

Task queues
Tasks queues receive tasks and their related data, runs them, then delivers their results. They can support scheduling and can be used to run computationally-intensive jobs in the background.

Celery has support for scheduling and primarily has python support.

Back pressure
If queues start to grow significantly, the queue size can become larger than memory, resulting in cache misses, disk reads, and even slower performance. Back pressure can help by limiting the queue size, thereby maintaining a high throughput rate and good response times for jobs already in the queue. Once the queue fills up, clients get a server busy or HTTP 503 status code to try again later. Clients can retry the request at a later time, perhaps with exponential backoff.

Disadvantage(s): asynchronism
Use cases such as inexpensive calculations and realtime workflows might be better suited for synchronous operations, as introducing queues can add delays and complexity.

Source: Intro to architecting systems for scale

Asynchronous workflows help reduce request times for expensive operations that would otherwise be performed in-line. They can also help by doing time-consuming work in advance, such as periodic aggregation of data.

Message queues
Message queues receive, hold, and deliver messages. If an operation is too slow to perform inline, you can use a message queue with the following workflow:

An application publishes a job to the queue, then notifies the user of job status
A worker picks up the job from the queue, processes it, then signals the job is complete
The user is not blocked and the job is processed in the background. During this time, the client might optionally do a small amount of processing to make it seem like the task has completed. For example, if posting a tweet, the tweet could be instantly posted to your timeline, but it could take some time before your tweet is actually delivered to all of your followers.

Redis is useful as a simple message broker but messages can be lost.

RabbitMQ is popular but requires you to adapt to the ‘AMQP’ protocol and manage your own nodes.

Amazon SQS is hosted but can have high latency and has the possibility of messages being delivered twice.

Task queues
Tasks queues receive tasks and their related data, runs them, then delivers their results. They can support scheduling and can be used to run computationally-intensive jobs in the background.

Celery has support for scheduling and primarily has python support.

Back pressure
If queues start to grow significantly, the queue size can become larger than memory, resulting in cache misses, disk reads, and even slower performance. Back pressure can help by limiting the queue size, thereby maintaining a high throughput rate and good response times for jobs already in the queue. Once the queue fills up, clients get a server busy or HTTP 503 status code to try again later. Clients can retry the request at a later time, perhaps with exponential backoff.

Disadvantage(s): asynchronism
Use cases such as inexpensive calculations and realtime workflows might be better suited for synchronous operations, as introducing queues can add delays and complexity.

Source: SQL & NoSQL, a brief history

Abstraction: nested map ColumnFamily<RowKey, Columns<ColKey, Value, Timestamp>>

A wide column store’s basic unit of data is a column (name/value pair). A column can be grouped in column families (analogous to a SQL table). Super column families further group column families. You can access each column independently with a row key, and columns with the same row key form a row. Each value contains a timestamp for versioning and for conflict resolution.

Google introduced Bigtable as the first wide column store, which influenced the open-source HBase often-used in the Hadoop ecosystem, and Cassandra from Facebook. Stores such as BigTable, HBase, and Cassandra maintain keys in lexicographic order, allowing efficient retrieval of selective key ranges.

Wide column stores offer high availability and high scalability. They are often used for very large data sets.
